# Решения

Формат: дата · решение · почему · что это меняет.

- 2026-10-15 · Стек: FastAPI + PostgreSQL + Next.js, слайсер PrusaSlicer CLI на сервере, редакторы на OpenSCAD CLI. · Python владелец читает; слайсер в браузере клиенту не нужен — нужны цена, срок и картинка; OpenSCAD даёт параметрические детали без своего CAD-ядра. · Браузерный слайсер (модуль 4б из идеи) не делаем.
- 2026-10-15 · Postgres — источник истины по заказам. Google-таблица «Учет 3D-печати ТУЦ» получает экспорт, а не пишется напрямую. · Таблица не выдерживает параллельные записи и не хранит файлы. · Superset подключается к Postgres read-only пользователем.
- 2026-10-15 · Ветки: `dev` — ночные сборки, `main` — прод через PR владельца. · Защита прода от сломанной ночи. · Деплой staging с dev, prod с main (B10).
- 2026-10-16 · Tailwind v4 через `@tailwindcss/postcss`, без tailwind.config. · Меньше файлов, актуальная версия. · Стили — в `web/app/globals.css`.
- 2026-10-18 · Загрузки (B02) хранятся на диске: `DATA_DIR/uploads/<id>/model.<ext>` + `meta.json`, без БД. · В проекте ещё нет Postgres-моделей и Alembic; тянуть их ради одной таблицы в B02 — лишний объём. · В B06 вместе с заказами появляется таблица `models`, meta.json переезжает в неё; файлы остаются на диске.
- 2026-10-18 · Незамкнутую сетку не отклоняем: пробуем закрыть дыры (`trimesh.repair.fill_holes`), иначе сохраняем с предупреждением `not_watertight`. · Клиент часто не умеет чинить STL; слайсер (B04) обычно справляется сам. · Цена по такой модели считается по приблизительному объёму — об этом говорит предупреждение на странице.
- 2026-10-18 · Единицы файла хранятся на сервере (`units` в meta загрузки, mm | inch), все числа `mesh` — всегда в мм. · STL единиц не содержит; если клиент сказал «файл в дюймах», цена (B05) и слайсер (B04) должны считать по масштабу 25,4 — поэтому решение живёт в API, а не только в браузере. · B04 при слайсинге применяет `UNITS[meta.units]` к модели.
- 2026-10-18 · Worker — не отдельный пакет, а тот же код `api/` в контейнере с PrusaSlicer (`worker/Dockerfile`, задачи в `api/app/worker.py`, очередь arq/Redis). · Один pyproject, одни тесты, одна модель настроек; слайсеру нужны те же `meta.json` и `DATA_DIR`. · Если `REDIS_URL` пуст, API слайсит сам, синхронно — только для разработки и тестов.
- 2026-10-18 · Результат слайсинга хранится файлом `DATA_DIR/uploads/<id>/slices/<материал>[_supports].json` + G-code рядом; один расчёт на пару «материал + поддержки», повторно не считаем. · БД появится в B06; G-code потом пойдёт на принтер. · В B06 запись переедет в таблицу `print_jobs`, файлы останутся на диске.
- 2026-10-18 · Профили слайсера — три ini-файла (`profiles/printer.ini`, `print.ini`, `filament/<материал>.ini`), грузятся через `--load` по очереди; принтер обобщённый FDM 250×210×220, сопло 0.4, слой 0.2. · Владелец может заменить любой файл экспортом из своего PrusaSlicer, код менять не нужно. · Список материалов (`MATERIALS` в `app/slicer.py`) = список файлов в `profiles/filament/`; B05 берёт цены по тем же именам из `pricing.yaml`.
- 2026-10-19 · Формула цены (B05) читается так: граммы и часы от слайсера — на одно изделие, умножаем на тираж; `min_order` сравниваем с суммой за печать всего тиража (`unit_price × qty`), а постобработка (за штуку) и доставка (за заказ) прибавляются сверху; итог округляем до рубля. · В SPEC формула записана для одного изделия и не говорит, где стоит тираж; так минимальный заказ не «съедает» доставку, а скидка за тираж действует на печать, не на доставку. · Все деньги — в `api/app/pricing.py::calc_price`, ответ `/quote` содержит ставки и разложение суммы, чтобы владелец видел, откуда цифра.
- 2026-10-19 · Расчёт цены (quote) хранится файлом `DATA_DIR/uploads/<id>/quotes/<quote_id>.json`, id = `<upload_id>-<6 hex>`; `pricing.yaml` читается один раз на процесс (кэш). · БД появится в B06 — там quote станет таблицей `quotes`, заказ будет ссылаться на её id; менять цены на лету пока незачем — после правки yaml перезапускается API. · B06 берёт `GET /api/v1/quotes/{id}` как основу заказа.
- 2026-10-19 · БД (B06): SQLAlchemy 2 + Alembic, таблица `orders` (`api/app/models.py`, миграции в `api/alembic/versions/`), миграции применяются при старте контейнера api (`alembic upgrade head && uvicorn …`). Тесты и локальный прогон без Postgres — на SQLite-файле (`DATABASE_URL=sqlite:///…`), тот же код. · Postgres в песочнице сборки нет; SQLAlchemy одинаково пишет в оба, а тест `test_alembic_matches_models` следит, чтобы миграции не разошлись с моделями. · Новая таблица = правка `models.py` + файл миграции; `Base.metadata.create_all` в проде не используется.
- 2026-10-19 · Заказ (B06) хранит ссылки `upload_id`/`quote_id` и полный снимок расчёта цены в колонке `quote` (JSON); загрузки, расчёты печати и цены остаются файлами в `DATA_DIR`, переезд их в таблицы `models`/`quotes`/`print_jobs` откладывается. · Ради одной таблицы заказов не стоит переписывать B02–B05; снимок нужен, чтобы цена в заказе не менялась после правки `pricing.yaml`. · Для SQL владельца ключевые поля (материал, тираж, сумма, статус, телефон) вынесены в колонки; детали — в `quote`.
- 2026-10-19 · Страница статуса заказа без логина: `/order/<token>`, token — 32 случайных hex-символа, выдаётся один раз при оформлении; по номеру заказа (`ТУЦ-12`) страница не открывается. · Кабинета клиента до B32 нет, а ссылку на статус нужно дать сразу. · B07/B08 отправляют клиенту именно эту ссылку.
- 2026-10-19 · Доставка выбирается на шаге расчёта цены и в заказ приходит из расчёта; форма заказа спрашивает только контакты, адрес (если курьер), комментарий и согласие на обработку ПДн. · Так цена в заказе всегда равна цене, которую клиент видел в расчёте. · Телефон нормализуется на сервере в `+7XXXXXXXXXX` (`app/orders.py::normalize_phone`).
- 2026-10-20 · Telegram-бот (B07) — не отдельный пакет `bot/`, а модуль `api/app/bot.py` (aiogram 3) в том же образе, что api; сервис `bot` в compose запускает `python -m app.bot`. Режим — long polling, без вебхука. · Боту нужны те же модели, настройки и БД, что API; отдельный pyproject дублировал бы код (как уже решено для worker). Polling не требует публичного адреса — бот заработает до деплоя (B10) даже с ноутбука. · Уведомление о новом заказе шлёт сам API (`app/telegram.py`, один HTTP-вызов Bot API через httpx, в фоне после ответа клиенту); бот только обрабатывает команды и кнопки. Кнопки под уведомлением и под карточкой из бота — одни и те же (`callback_data` вида `status:<id>:<статус>`).
- 2026-10-20 · Смена статуса заказа — одна функция `app/orders.py::change_status` (любой переход разрешён, запрещён только повтор того же статуса); бот предлагает кнопками лишь логичные шаги (`telegram.NEXT_STATUSES`: принят → оплачен/печатается/отменён → … → выдан; отменённый можно вернуть в «принят»). · Владелец — один, ему виднее; жёсткий автомат переходов только мешал бы (оплата наличными при самовывозе, возврат из отмены). · Админка (B09) и ЮKassa (B08, статус paid) зовут ту же функцию. Бот отвечает только чату `TELEGRAM_OWNER_CHAT_ID`, остальным — отказ.
- 2026-10-20 · ЮKassa (B08) подключена напрямую через REST API v3 (`api/app/payments.py`, httpx, два вызова: создать платёж и прочитать платёж), без пакета `yookassa`, который назван в SPEC. · Пакет — тонкая обёртка над теми же двумя вызовами с глобальной настройкой и `requests`; httpx уже есть (Telegram), а подменять транспорт в тестах проще, чем SDK. · Если понадобятся возвраты или чеки отдельным запросом — добавим вызовы в тот же модуль.
- 2026-10-20 · Статус платежа берём только из ответа ЮKassa `GET /v3/payments/{id}`: и по вебхуку, и когда клиент вернулся с формы (`/payment/check`), тело вебхука служит лишь поводом перечитать платёж. · Вебхуки ЮKassa не подписаны, а проверять IP-диапазоны хрупко; к тому же без публичного домена (до B10) вебхук не дойдёт вовсе, а возврат клиента на `/order/<token>?payment=check` сработает и на ноутбуке. · Идемпотентность: заказ становится «оплачен» только при переходе строки `payments` в `succeeded` впервые; повторный вебхук ничего не меняет и второго сообщения владельцу не шлёт. Если владелец уже перевёл заказ дальше (печатается), оплата статус не откатывает.
- 2026-10-20 · Платёж создаём с `capture: true` (одностадийно) и суммой = `orders.total`; чек 54-ФЗ вкладываем в платёж только если задан `YOOKASSA_VAT_CODE` (одна позиция «3D-печать по заказу ТУЦ-N» на всю сумму). · Владелец пока решает юрформу (ИП / самозанятый): самозанятому чек от нас не нужен, ИП с кассой ЮKassa — нужен; переключается одной переменной без правки кода. · Онлайн-оплата доступна только заказу в статусе «принят»; второй успешный платёж по заказу невозможен (409).
- 2026-10-20 · Админка (B09) — HTML-страницы прямо из FastAPI (`api/app/admin.py`, шаблоны Jinja2 в `api/app/templates/admin/`), путь `/admin`, вход — basic auth браузера (`ADMIN_USER` / `ADMIN_PASSWORD`; пустой пароль = админка выключена, 503). Caddy и `next.config` отправляют `/admin*` в api. · Basic auth сам работает при переходе по ссылке и при скачивании файла — не нужны ни форма входа, ни сессии, ни JS; страниц всего две (список и карточка), Next для них лишний. Защита формы смены статуса от подделки с чужого сайта — по заголовку `Sec-Fetch-Site`. · Смена статуса зовёт ту же `orders.change_status`, что бот и ЮKassa. Список отдаётся и как CSV (`/admin/orders.csv`, разделитель `;`, UTF-8 с BOM) — до экспорта в Google-таблицу (B11) владелец может выгружать заказы так. В тестах и деве на SQLite `lower()` подменён на питоновский (`app/db.py`), чтобы поиск по кириллице работал как в Postgres.
- 2026-10-20 · Деплой (B10): один VPS, на нём два стенда как два проекта compose — `/srv/tuc/prod` (ветка `main`, проект `tuc-prod`) и `/srv/tuc/staging` (ветка `dev`, проект `tuc-staging`), у каждого своя БД, Redis, `data/` и `.env`; HTTPS делает один общий Caddy (`deploy/edge`), который по домену отправляет запросы в контейнеры стенда по их именам `tuc-<стенд>-api-1` / `tuc-<стенд>-web-1` через внешнюю docker-сеть `tuc_edge`. · Второй VPS ради staging владельцу не нужен, а два Caddy не поделят порты 80/443; имена контейнеров compose предсказуемы, и шаблон домена на них проще, чем сеть с алиасами. На сервере `docker-compose.yml` дополняется `deploy/compose.server.yml` через `COMPOSE_FILE` в `.env` стенда — локальный запуск не меняется. · Стенд с одной репликой на сервис (имя `-1`); staging закрыт от индексации заголовком `X-Robots-Tag`.
- 2026-10-20 · Деплой запускается из GitHub Actions только после зелёного CI (`workflow_run`) и по SSH выполняет на сервере `deploy/deploy.sh <коммит>`: `git reset --hard` + `docker compose up -d --build` + ожидание healthcheck api. Секреты — репозиторные (`DEPLOY_SSH_HOST`, `DEPLOY_SSH_KEY`), без GitHub Environments. · Сервер сам тянет код по read-only deploy key — владелец видит на сервере обычный git-клон и может развернуть или откатить руками той же командой; environments в приватном репозитории — лишняя настройка. · Пока секретов нет, job «Deploy» завершается успешно с пометкой «не настроен», чтобы CI не был красным до появления VPS. Файлы репозитория на сервере не правят — всё через git.
- 2026-10-20 · В `.env.example` у пустых переменных комментарий стоит строкой выше, а не после `=`. · `docker compose` читает `KEY=   # текст` как значение «# текст» (проверено `docker compose config`): бот получил бы такой «токен», а ЮKassa считалась бы настроенной; pydantic-settings/python-dotenv читают то же как пустую строку, поэтому локально без Docker ошибка не проявлялась. · Тест `api/tests/test_env_example.py` не даёт вернуть такой комментарий и следит, что все настройки `Settings` перечислены в `.env.example`.
- 2026-10-20 · Google-таблица (B11): worker раз в ночь (cron arq, 05:05 МСК) переписывает целиком один лист `GOOGLE_SHEET_TAB` («Заказы (сайт)») — заголовок + строка на заказ, те же колонки, что в CSV админки (`api/app/export.py`); остальные листы таблицы не трогаем. В Sheets API v4 ходим напрямую через httpx (три вызова: листы, очистить, записать), токен — по JWT сервисного аккаунта (PyJWT), без `gspread`, названного в SPEC. · Полная перезапись проще и надёжнее дозаписи: нет сверки по номерам, смена статуса и оплата сами попадают в таблицу, а владелец строит формулы и сводные на своих листах со ссылкой на этот. gspread тянет google-auth с `requests` и глобальной настройкой — подменить в тестах сложнее, чем транспорт httpx (как уже сделано для ЮKassa). · Значения пишем как RAW (телефон остаётся текстом с «+», даты — текст «19.10.2026 23:41» по Москве). Ключ лежит в `secrets/google-sa.json` (папка в `.gitignore`, в контейнер монтируется `/srv/secrets`). Выгрузка руками — `python -m app.sheets`.
- 2026-10-20 · Superset (B11) подключается к Postgres стенда read-only пользователем `tuc_ro` (`deploy/readonly-user.sh` + `.sql`: `SELECT` на все таблицы схемы public, включая будущие, и `default_transaction_read_only`), а Postgres на сервере опубликован только на `127.0.0.1` (prod 5433, staging 5434 — `POSTGRES_LOCAL_PORT` в `compose.server.yml`), доступ с ноутбука — через SSH-туннель. · Superset на том же VPS с 4 ГБ не поместится рядом со слайсером; открывать Postgres в интернет не хотим — туннель по уже имеющемуся ключу `deploy` ничего не стоит. · Пароль `tuc_ro` скрипт пишет в `.env` стенда (`POSTGRES_RO_PASSWORD`), в репозиторий не попадает.
- 2026-10-20 · События воронки (B12) пишет сервер в таблицу `events` в момент шага (upload, quote, order, payment_started, paid), без JS-трекинга и cookies. `paid` — только онлайн-оплата ЮKassa; «оплачен» руками владельца (наличные) в событиях нет, для этого есть `orders.status`. Запись события никогда не ломает основной сценарий: ошибка БД → предупреждение в лог. Без внешнего ключа на `orders` — журнал переживает удаление заказа. · Владелец считает воронку в SQL/Superset, ему нужны надёжные серверные факты, а не клики; клиентский id посетителя (несколько загрузок одного человека) добавим, когда понадобится — это заголовок с сайта и колонка `visitor_id`. · Сводка за 30 дней в админке, SQL — `docs/ANALYTICS.md`.
- 2026-10-21 · Автоудаление файлов (B15) — ночной cron в worker (`app/worker.py::cleanup_files` → `app/cleanup.py`, 04:35 МСК) удаляет папку загрузки `DATA_DIR/uploads/<id>/` целиком (модель, meta.json, расчёты печати с G-code, расчёты цены); записи `orders`/`payments`/`events` не трогаем — заказ хранит снимок цены и имя файла. Сроки — из политики ПДн: без заказа — 30 дней от загрузки; с заказами — только когда все заказы по загрузке закрыты (`done`/`cancelled`) и последний закрыт больше 365 дней назад (по `orders.updated_at`); заказ в работе держит файл без срока. Отменённый заказ считаем «оформленным» и ждём те же 12 месяцев, а не 30 дней — политика для оформленных заказов отдельного срока отмены не называет, а одно правило проще. Сроки — `CLEANUP_UPLOADS_DAYS` / `CLEANUP_ORDER_FILES_DAYS`, 0 = правило выключено. · Отдельной таблицы удалений не завели: факт удаления виден в логе worker и по отсутствию кнопки «Скачать файл» в админке. · Удаление/обезличивание самих заказов через 5 лет (тоже обещано в политике) — отдельная задача B35, спешить некуда.
- 2026-10-21 · Юридические страницы (B13) — оферта `/offer`, политика ПДн `/policy`, «О студии» `/about`, «Контакты» `/contacts` — обычные статические страницы Next (`web/app/<имя>/page.tsx`, общие кирпичики в `web/components/Doc.tsx`), а реквизиты и контакты студии — в одном файле `web/lib/company.ts` (`COMPANY`), откуда их берут все четыре страницы и подвал. Пустое поле показывается клиенту как «уточняется», а над документом — пометка «предварительная редакция»; она исчезает сама, когда заполнены обязательные поля (`REQUIRED_FIELDS`). · Юрформа владельца ещё не выбрана (ИП / самозанятый), а оферта и политика должны быть на сайте раньше оплат; тексты в JSX, а не в Markdown — не нужен пакет-рендерер, а править абзац владелец может прямо в файле. Реквизиты не в `.env`: их много, они публичны, и менять их без пересборки web всё равно нельзя. · Галочка в форме заказа теперь ссылается на оферту и политику; политика описывает только реальные потоки данных (ЮKassa, Telegram владельца, Google-таблица, курьер) и обещает сроки хранения файлов — отсюда задача B15 (автоудаление).
